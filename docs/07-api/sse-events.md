> Trạng thái: **Review** · Cập nhật: 2026-09-28 · DOC-33

> Phụ thuộc: [DOC-09](../03-architecture/messaging-contracts.md) §6, [DOC-26](../06-design/realtime-delivery.md), [DOC-23](../06-design/analytics.md) §10, [DOC-20](../06-design/etl-streaming.md) §8, [DOC-32](api-endpoints.md), DR-41, DR-42, ADR-0016, ADR-0023, ADR-0026

> Người dùng chính: publisher sự kiện UI (etl-stream, etl-batch, triage-worker, api), app `api` (DOC-26), frontend (hook `useRealtime`, P5-03), contract test

## 1. Phạm vi

Tài liệu này là **hợp đồng** của từng kiểu sự kiện: kênh, audience, ai phát, khóa Kafka, payload trên topic `pti.events.ui` và trên luồng SSE `GET /api/v1/stream`. Cách vận chuyển (consumer theo pod, ring buffer, `Last-Event-ID`, giới hạn kết nối) nằm ở DOC-26.

Nguyên tắc (DR-42, ADR-0026): sự kiện là **gợi ý thay đổi**, không phải nguồn sự thật. Publish best-effort sau commit; mất một sự kiện thì client vẫn đúng nhờ refetch khi nối lại, khi nhận `resync`, và refetch định kỳ 60 giây. Vì vậy payload chỉ cần đủ để cập nhật UI ngay, không cần đủ để dựng lại toàn bộ trạng thái.

## 2. Envelope

### 2.1 Trên Kafka (`pti.events.ui`)

Envelope snake_case như DOC-09 §6. **`data` luôn là camelCase**, vì API chuyển nó nguyên văn sang SSE mà không đổi tên khóa.

```json
{
  "id": "01J8ZK3V5Q7X2M4N6P8R0T2V4W",
  "type": "bunching.opened",
  "channel": "alerts",
  "audience": "OPERATIONS",
  "occurred_at": "2026-09-29T21:19:31.020Z",
  "source_record_ts": "2026-09-29T21:19:30.107Z",
  "route_id": "18",
  "data": { "id": "6f1c2a9e-4b1d-5c8e-9a2f-3d4e5f6a7b8c", "routeId": "18" }
}
```

Mọi publisher dùng chung `UiEventPublisher` trong module `common`:

```java
package dev.pti.common.events;

public enum UiChannel { VEHICLES, ALERTS, JOBS, DLQ }            // serialized lowercase
public enum Audience { PUBLIC, OPERATIONS, ENGINEERING }

public record UiEvent(String id,                  // ULID, generated by UiEvent.of(...)
                      String type,
                      UiChannel channel,
                      Audience audience,
                      Instant occurredAt,         // wall clock
                      @Nullable Instant sourceRecordTs,
                      @Nullable String routeId,
                      String key,                 // Kafka key, see §3
                      Map<String, Object> data) {
  public static UiEvent of(String type, UiChannel channel, Audience audience, String key,
                           @Nullable String routeId, @Nullable Instant sourceRecordTs,
                           Map<String, Object> data) { /* ULID via ulid-creator (monotonic) */ }
}

public interface UiEventPublisher {
  /** Best-effort, after commit. Never throws; failures are logged and counted. */
  void publish(UiEvent event);
  void publishAll(List<UiEvent> events);
}
```

- `KafkaUiEventPublisher` gửi bằng producer `acks=1`, `linger.ms=5`, `enable.idempotence=false` (mất hoặc trùng đều chấp nhận được; client dedupe theo `id`). Lỗi gửi: log `WARN` và tăng `pti_ui_events_publish_errors_total{type}`.
- Gọi `publish` **sau commit**: trong code có transaction dùng `TransactionSynchronization.afterCommit` (hoặc `@TransactionalEventListener(phase = AFTER_COMMIT)`), không bao giờ gọi bên trong transaction.
- Kích thước `data` ≤ 64 KiB (kiểm trong `of`; vượt thì ném `IllegalArgumentException`, vì đó là lỗi lập trình). `vehicles.batch` là sự kiện lớn nhất (≈ 60 xe × 250 byte ≈ 15 KiB).

### 2.2 Trên SSE

Mỗi sự kiện là một khung SSE:

```
id: 01J8ZK3V5Q7X2M4N6P8R0T2V4W
event: bunching.opened
data: {"id":"01J8ZK3V5Q7X2M4N6P8R0T2V4W","type":"bunching.opened","channel":"alerts","occurredAt":"2026-09-29T21:19:31.020Z","routeId":"18","data":{"id":"6f1c2a9e-4b1d-5c8e-9a2f-3d4e5f6a7b8c","routeId":"18"}}

```

| Trường SSE | Giá trị |
| --- | --- |
| `id:` | `id` của envelope. `heartbeat` và `resync` **không** có dòng `id:` để không làm lệch `Last-Event-ID` |
| `event:` | `type` |
| `data:` | JSON một dòng: `id`, `type`, `channel`, `occurredAt`, `routeId` (nếu có), `data` (đã qua projection theo quyền, §4) |
| `retry:` | `1000`, gửi một lần ở đầu kết nối |

- `audience` và `source_record_ts` **không** được gửi xuống client. Audience chỉ dùng để lọc; `source_record_ts` chỉ dùng để đo `pti_end_to_end_latency_seconds` lúc emit (DR-57).
- Client xử lý sự kiện có `type` lạ bằng cách bỏ qua (tương thích tiến, DOC-31 §12).
- Client dedupe theo `id` (LRU 1.000 id), vì fallback của `Last-Event-ID` có thể gửi lại vài sự kiện (DOC-26 §5).

## 3. Danh mục

| Kiểu | Kênh | Audience | Publisher | Khóa Kafka | Trong ring buffer |
| --- | --- | --- | --- | --- | --- |
| `vehicles.batch` | `vehicles` | `PUBLIC` | etl-stream (`VehiclesBatchPublisher`, DOC-20 §8) | `route_id` | Không |
| `bunching.opened`, `bunching.closed` | `alerts` | `OPERATIONS` | etl (analytics, DOC-23 §10.3) | id episode | Có |
| `disruption.opened`, `disruption.closed` | `alerts` | audience hiện tại của alert | etl (analytics) | id episode | Có |
| `dispatch.suggested` | `alerts` | `OPERATIONS` | triage-worker (P6, DOC-24) | id bunching | Có |
| `alert.created` | `alerts` | audience của dòng | etl (analytics), api (webhook Alertmanager) | id alert | Có |
| `alert.updated` | `alerts` | audience của dòng sau khi đổi | etl (analytics), triage-worker, api (ack, webhook resolved) | id alert | Có |
| `alert.retracted` | `alerts` | audience **trước** khi đổi | triage-worker (FR-09.5) | id alert | Có |
| `job.run` | `jobs` | `ENGINEERING` | etl-batch (`JobRunEventListener`) | `job:<jobExecutionId>` | Có |
| `dlq.changed` | `dlq` | `ENGINEERING` | etl-stream (`CREATED`), etl-batch, triage-worker, api (`UPDATED`) | `CREATED`, `BULK_UPDATED`: `source`; `UPDATED`: id dead letter | Có |
| `resync` | mọi kênh | — | api (tự sinh) | — | Không |
| `heartbeat` | — | — | api (tự sinh) | — | Không |

Thay đổi so với DOC-09 §6 (đã cập nhật ở đó): thêm `alert.retracted`; `api` là publisher; khóa của `job.run` là `job:<jobExecutionId>` (thứ tự sự kiện của một lần chạy được giữ trong một partition); khóa của `dlq.changed` `CREATED` là `source`.

## 4. Quyền và projection

| Audience của sự kiện | Anonymous | viewer, operator |
| --- | --- | --- |
| `PUBLIC` | Nhận, qua projection công khai | Nhận đầy đủ |
| `OPERATIONS`, `ENGINEERING` | Không nhận | Nhận đầy đủ |

- Kênh `jobs` và `dlq` cần viewer ngay khi mở kết nối (DOC-32 E-70); kênh `vehicles` và `alerts` mở cho mọi người.
- **Projection công khai** áp cho anonymous, cùng danh sách cho phép với REST (DOC-32 E-12, E-20):

| Kiểu | Khóa `data` giữ lại cho anonymous |
| --- | --- |
| `vehicles.batch` | Toàn bộ (§5.1 không có trường nhạy cảm) |
| `disruption.opened`, `disruption.closed` | `id`, `routeId`, `directionId`, `episodeStart`, `episodeEnd`, `currentAvgDelaySeconds`, `affectedStopIds`, `closeReason` |
| `alert.created`, `alert.updated` | Như REST E-20: bỏ `acknowledgedBy`, `acknowledgedAt`; `body` chỉ giữ khóa cho phép theo `type` |
| `alert.retracted` | `id`, `routeId` |

  Projection là một bảng tĩnh trong `SseProjection` (api), có unit test cho từng kiểu. Kiểu không có trong bảng mà audience `PUBLIC` → không gửi cho anonymous (an toàn mặc định) và log `WARN` một lần.
- Lọc `routeId` của kết nối (DOC-32 E-70) áp cho sự kiện có `routeId`; sự kiện không có `routeId` (ví dụ alert `INFRA`) luôn được gửi.

## 5. Payload

Thời điểm là ISO-8601 UTC; id insight là UUID; enum giữ nguyên giá trị DB (DOC-31 §3).

### 5.1 `vehicles.batch`

Vị trí mới nhất của các xe **một tuyến** có thay đổi trong giây vừa qua.

```json
{
  "routeId": "18",
  "vehicles": [
    {
      "vehicleId": "1203",
      "tripId": "27371245-AUG26-MVS-BUS-Weekday-01",
      "directionId": 0,
      "lat": 44.948121,
      "lon": -93.278004,
      "bearing": 358.0,
      "speedMps": 7.4,
      "currentStatus": "IN_TRANSIT_TO",
      "stopId": "51420",
      "currentStopSequence": 14,
      "occupancyStatus": "MANY_SEATS_AVAILABLE",
      "eventTimestamp": "2026-09-29T21:19:30Z"
    }
  ]
}
```

- Không có `delaySeconds`, `headsign`, `label`: frontend giữ các trường này từ snapshot `GET /vehicles/live` và chỉ cập nhật vị trí. Xe mới xuất hiện (chưa có trong snapshot) được vẽ ngay; thông tin phụ đến ở lần refetch kế tiếp (60 giây).
- API gộp thêm một lần ở phía mình: mỗi kết nối nhận tối đa một `vehicles.batch` mỗi tuyến mỗi giây (DOC-26 §6). Hai sự kiện cùng tuyến trong một giây được hợp nhất theo `vehicleId` (giữ `eventTimestamp` mới hơn); `id` của khung SSE là `id` của sự kiện mới nhất được gộp.
- Xe biến mất (mất tín hiệu quá 5 phút) **không** có sự kiện riêng: frontend tự ẩn xe có `eventTimestamp < businessNow − 5 phút`, dùng `businessNow` của `heartbeat`.

### 5.2 `bunching.opened`, `bunching.closed`

```json
{
  "id": "6f1c2a9e-4b1d-5c8e-9a2f-3d4e5f6a7b8c",
  "routeId": "18",
  "directionId": 0,
  "vehicleLeader": "1187",
  "vehicleFollower": "1203",
  "gapSeconds": 112,
  "headwaySeconds": 600,
  "stopId": "51418",
  "episodeStart": "2026-09-29T21:12:15Z"
}
```

`bunching.closed`: `id`, `routeId`, `episodeEnd`, `closeReason`, `minGapSeconds` (DOC-23 §10.3). Frontend: thêm/bỏ overlay của hai xe trên bản đồ, refetch `GET /insights/bunching` nếu đang mở.

### 5.3 `disruption.opened`, `disruption.closed`

```json
{
  "id": "9d8e7f6a-5b4c-5d3e-8f2a-1b0c9d8e7f6a",
  "routeId": "18",
  "directionId": 0,
  "episodeStart": "2026-09-29T20:58:00Z",

  "baselineMeanSeconds": 61.4,

```

`disruption.closed`: `id`, `routeId`, `directionId`, `episodeEnd`, `closeReason`, `peakZScore`. Frontend: refetch `GET /stops/{id}` nếu trạm đang xem thuộc tuyến đó; refetch danh sách disruption.

```json
  "bunchingId": "6f1c2a9e-4b1d-5c8e-9a2f-3d4e5f6a7b8c",
```

### 5.5 `alert.created`, `alert.updated`

Chính bản ghi alert, cùng dạng với phần tử của `GET /alerts` (DOC-32 E-20) và thêm `resolvedAt` khi có:

```json
{
  "id": "0a4c7e1f-2b3d-5e6f-8a9b-1c2d3e4f5a6b",
  "type": "DISRUPTION",
  "severity": 2,
  "audience": "PUBLIC",
  "routeId": "18",
  "refTable": "insight.insight_service_disruption",
  "refId": "9d8e7f6a-5b4c-5d3e-8f2a-1b0c9d8e7f6a",
  "title": "Delays on route 18 northbound",
  "body": { "disruptionId": "9d8e7f6a-5b4c-5d3e-8f2a-1b0c9d8e7f6a", "peakZScore": 4.44 },
  "createdAt": "2026-09-29T20:59:31Z",
  "link": "/map?route=18&disruption=9d8e7f6a-5b4c-5d3e-8f2a-1b0c9d8e7f6a"
}
```

- `link` không có trong message Kafka; API thêm vào khi chiếu sự kiện ra SSE, bằng cùng `AlertLinkBuilder` với E-20 (DOC-32).
- Frontend thay thế bản ghi cùng `id` trong cache (không merge từng trường), vì sự kiện luôn mang bản ghi đầy đủ sau thay đổi.
- `alert.updated` được phát khi: severity tăng, episode đóng (`resolvedAt`), ack (`acknowledgedBy`, `acknowledgedAt`), Alertmanager `resolved`, triage-worker đổi `title`/`body` hoặc **mở rộng** audience.

### 5.6 `alert.retracted`

Phát khi audience của alert bị **thu hẹp** (ví dụ FR-09.5 chuyển disruption từ `PUBLIC` sang `ENGINEERING`). Sự kiện mang audience **cũ**, để chính những client đã thấy alert nhận được lệnh gỡ nó.

```json
{ "id": "0a4c7e1f-2b3d-5e6f-8a9b-1c2d3e4f5a6b", "routeId": "18" }
```

- triage-worker phát **hai** sự kiện sau commit: `alert.retracted` (audience cũ) rồi `alert.updated` (audience mới). Client đã đăng nhập nhận cả hai và kết quả cuối là alert còn hiển thị với audience mới; anonymous chỉ nhận `alert.retracted` và gỡ alert.
- Nếu client nhận hai sự kiện theo thứ tự ngược (khóa giống nhau nên cùng partition, thứ tự được giữ; ngược chỉ xảy ra khi replay từ buffer lỗi), `alert.retracted` đến sau sẽ gỡ alert; refetch 60 giây sửa lại. Chấp nhận được.

### 5.7 `job.run`

```json
{
  "runId": "job:4127",
  "kind": "BATCH_JOB",
  "name": "RawZoneReplayJob",
  "status": "STARTED",
  "startedAt": "2026-09-29T20:40:02Z",
  "readCount": 212000,
  "writeCount": 211500,
  "skipCount": 500,
  "jobExecutionId": 4127
}
```

- `JobRunEventListener` (etl-batch, đăng ký cho mọi job bằng `JobRegistry`): phát khi job bắt đầu (`beforeJob`), khi kết thúc (`afterJob`, thêm `endedAt`, `exitCode`, `exitMessage` ≤ 500 ký tự), và sau mỗi chunk commit (`ChunkListener.afterChunk`) nhưng **tối đa một lần mỗi 2 giây** cho mỗi execution (`pti.etl.ui-events.job-throttle`).
- Bộ đếm lấy từ `StepExecution` đang chạy cộng với các step đã xong, cùng cách tính với `ops_job_run_v`.
- Micro-batch streaming **không** phát `job.run` (quá dày; 4 listener × 60 lần/phút). Timeline của stream được frontend refetch từ `GET /etl/jobs/summary` mỗi 10 giây khi màn hình mở.

### 5.8 `dlq.changed`

Ba dạng, phân biệt bằng `kind` (`CREATED`, `UPDATED`, `BULK_UPDATED`):

```json
{ "kind": "CREATED", "source": "GTFS_RT_VEHICLE_POSITION", "count": 12, "lastCreatedAt": "2026-09-29T21:18:47Z" }
```

```json
{
  "kind": "UPDATED",
  "id": "0192f5b2-8d9e-7a0b-9c1d-2e3f4a5b6c7d",
  "source": "GTFS_RT_VEHICLE_POSITION",
  "status": "REPLAY_REQUESTED",
  "previousStatus": "MANUAL",
  "action": "REPLAY_REQUESTED",
  "actor": "user:operator"
}
```

```json
{ "kind": "BULK_UPDATED", "source": "GTFS_RT_TRIP_UPDATE", "status": "RESOLVED", "count": 938 }
```

| Dạng | Ai phát | Khi nào |
| --- | --- | --- |
| `CREATED` | etl-stream (`DlqEventAggregator`) | Gom số dòng DLQ mới theo nguồn, mỗi giây tối đa một sự kiện mỗi nguồn |
| `CREATED` | etl-batch | Sau step replay có `dlq_inserted > 0`, một sự kiện mỗi nguồn |
| `UPDATED` | triage-worker | Mỗi lần chuyển trạng thái (`TRIAGED`, `PENDING_CONFIRM`, `MANUAL`, `REPLAY_REQUESTED` tự động) |
| `UPDATED` | etl-batch | `DlqReplayJob` kết thúc (`REPLAYED` hoặc về `NEW`); `RawZoneReplayJob` đánh dấu `RESOLVED` **gộp**: nhiều hơn 20 dòng trong một chunk thì phát một sự kiện `BULK_UPDATED` cho mỗi nguồn và trạng thái thay cho từng dòng |
| `UPDATED` | api | Sau mỗi thao tác của DOC-32 §7 |

Frontend: `CREATED`/`BULK_UPDATED` → refetch trang đầu của danh sách DLQ và summary (debounce 2 giây); `UPDATED` → cập nhật dòng cùng `id` nếu đang hiển thị, rồi refetch chi tiết nếu đang mở.

### 5.9 `resync`

```
event: resync
data: {"type":"resync","occurredAt":"2026-09-29T21:25:01Z","data":{"reason":"BUFFER_EXPIRED","channels":["alerts","jobs"]}}

```

| `reason` | Khi nào (DOC-26) |
| --- | --- |
| `BUFFER_EXPIRED` | `Last-Event-ID` cũ hơn ring buffer (mất kết nối > 5 phút), hoặc id không nhận ra được |
| `SLOW_CLIENT` | Queue của kết nối đầy; server bỏ các sự kiện chưa gửi và yêu cầu client đồng bộ lại |
| `CONSUMER_RESET` | Consumer của pod bị gán lại partition và mất liên tục (rebalance, lỗi Kafka) |

Frontend invalidate mọi query key thuộc `channels` (bảng ở DOC-26 §9) rồi refetch.

### 5.10 `heartbeat`

```
event: heartbeat
data: {"type":"heartbeat","data":{"serverTime":"2026-09-29T21:19:45Z","businessNow":"2026-09-29T21:19:45Z"}}

```

Mỗi 15 giây trên mọi kết nối. Client coi kết nối chết nếu 45 giây không nhận được gì (DOC-26 §8). `businessNow` giúp frontend tính tuổi dữ liệu mà không phụ thuộc đồng hồ máy người dùng.

## 6. Tiến hóa hợp đồng

- Thêm khóa vào `data`, thêm kiểu sự kiện mới: tương thích, làm tại chỗ. Kiểu mới phải được thêm vào bảng §3 và projection §4 (nếu audience có thể là `PUBLIC`).
- Đổi tên, xóa khóa, đổi nghĩa: tạo kiểu mới (`…v2`), phát song song một phiên bản, rồi bỏ kiểu cũ.
- Contract test (DR-44): mỗi kiểu có JSON Schema trong `backend/common/src/main/resources/schemas/ui-events/<type>.schema.json`. Test của publisher kiểm payload nó sinh ra; test của api kiểm projection; frontend sinh type TypeScript từ cùng schema (P5-02).
