# Contributing

Thanks for looking at Public Transport Intelligence. This is a single-maintainer project, so the rules below are
mainly there to keep the history readable and CI meaningful.

## Before you start

- Read [docs/09-operations/local-dev.md](docs/09-operations/local-dev.md) to set up the tools (`mise install`) and run
  the stack (`make secrets up`).
- Work items come from the master plan ([docs/00-master-plan.md](docs/00-master-plan.md)). A task is ready when the
  documents it references are `Approved` and its acceptance criteria are measurable (master plan §7.1).
- The design documents under `docs/` are written in Vietnamese. **Everything else is English**: code, comments, logs,
  API error messages, UI text, commit messages, PR titles and descriptions, test names (DR-61).

## Repository layout

| Directory | Stack | Build tool |
| --- | --- | --- |
| `backend/` | Java 25, Spring Boot 4 (Gradle multi-module) | `backend/gradlew` |
| `frontend/` | React, TypeScript, Vite | `pnpm` |
| `deploy/` | Docker Compose, k3d, Helm, Kafka Connect, Chaos Mesh | `docker`, `helmfile` |
| `experiments/` | Python experiment runner | `uv` |

The `Makefile` at the repository root is the entry point for all of them (`make help`). The full tree is in
[ADR-0030](docs/04-adr/0030-monorepo-layout.md).

## Branches and pull requests

- `dev` is the integration branch and must always build.
- The maintainer commits small, self-contained changes directly to `dev`. Everyone else uses a short-lived branch named `feat/…`, `fix/…`, `docs/…`, `chore/…` or `test/…` and opens a pull
  request into `dev`. Pull requests are squash-merged, so the PR title becomes the commit message.
- A change that crosses stacks (an endpoint and its frontend types, a topic and its consumer) goes in one PR.
- Fill in the pull request template, including the plan item (`Pn-xx`) and the docs you touched.

## Commit messages

Commits and PR titles follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <summary in the imperative mood>
```

- Types: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`.
- Scopes: a module or area such as `common`, `etl`, `api`, `sim`, `db`, `deploy`, `frontend`, `experiments`, `ci`.
- Example: `feat(etl): add scan-mode fallback`.

## Code conventions

- Java is formatted by Spotless with palantir-java-format. Run `make fmt` before committing.
- Packages are organised by feature, not by layer. No Lombok.
- Flyway migrations are named `V<n>__<description>.sql`. Never edit a migration that has been merged; add a new one.
- Every threshold lives in configuration and is documented in DOC-29
  ([configuration-reference.md](docs/06-design/configuration-reference.md)).
- Never commit secrets. `.env` is generated by `make secrets`; `.env.example` holds variable names only. CI runs
  gitleaks on every pull request.

## Before opening a pull request

```bash
make fmt lint test
```

Run `make it` as well when you touch persistence, Kafka or anything else covered by Testcontainers.

## Definition of Done

A change is done when CI is green, the new behaviour has tests, new metrics and configuration are documented, the
related docs are updated in the same PR (a changed decision gets a new ADR) and, if it has a runtime component, it
runs with `make up` (master plan §7.2).
